    UVM — the big picture¶

    UVM is a class library plus a set of conventions for building reusable, layered testbenches. The point of the layers is separation of concerns:

    • tests say what to do (which sequences, which configuration),
    • sequences say which transactions to generate,
    • drivers say how a transaction becomes pin wiggles,
    • monitors turn pin wiggles back into transactions,
    • scoreboards and reference models decide whether the DUT did the right thing,
    • the environment wires all of it together and is reused unchanged by every test.

    A generic UVM testbench¶

    flowchart TB
    subgraph TOP["tb_top (module)"]
        direction TB
        subgraph TEST["uvm_test_top : my_test"]
            direction TB
            subgraph ENV["tb : uvm_env"]
                direction LR
                subgraph UVC["agent (uvm_agent)"]
                    direction TB
                    SEQR["sequencer"]
                    DRV["driver"]
                    MON["monitor"]
                    SEQR -->|"seq_item_port / export<br/>get_next_item / item_done"| DRV
                end
                SB["scoreboard"]
                MON -->|"analysis port → imp"| SB
            end
        end
        CFG[("uvm_config_db<br/>virtual interfaces, knobs,<br/>default sequences")]
        FAC[("factory<br/>type_id::create, overrides")]
    end
    subgraph HW["hw_top (module)"]
        IF["interface"]
        DUT["DUT"]
        IF <--> DUT
    end
    DRV -->|"virtual interface"| IF
    IF -->|"virtual interface"| MON
    SEQ["sequence<br/>(uvm_sequence)"] -.->|"start / default_sequence"| SEQR
    CFG -.-> ENV
    FAC -.-> ENV

    Reading the diagram:

    • Everything inside uvm_test_top is a component: it has a name, a parent and goes through the phases (build, connect, run, report, ...).
    • A sequence is not a component. It is an object that is started on a sequencer and produces sequence items (transactions).
    • The two halves of the testbench — the class-based UVM side and the module-based hardware side — meet at the interface: the UVM side holds a virtual interface handle that was published in uvm_config_db.

    Concepts and where the labs introduce them¶

    Concept One-line summary Lab
    Data item methods do_print / do_copy / do_compare / do_pack behind print(), copy(), clone(), compare(), pack() (the course uses `uvm_field_* macros for the same thing) 1
    Phases build (top-down) → connect → end_of_elaboration → start_of_simulation → run (time passes) → extract → check → report 2, 3
    run_test() creates the test named by +UVM_TESTNAME and starts phasing 2
    Agent, active/passive is_active decides whether a driver and sequencer are built 3
    Default sequence uvm_config_wrapper::set(..., "run_phase", "default_sequence", type) 3
    Factory type_id::create() + set_type_override_by_type() 4
    Configuration uvm_config_int::set/get, check_config_usage() 4, 7
    Sequences body(), start_item / randomize() with / finish_item, seq.start(sequencer, this) for nesting 5
    Objections raise_objection / drop_objection keep run_phase alive; drain time 5, 6
    Virtual interface uvm_config_db #(virtual yapp_if) 6
    Virtual sequencer a sequencer that only holds handles to other sequencers 8
    TLM analysis uvm_analysis_port → uvm_analysis_imp / export / tlm_analysis_fifo 9A–9D
    Coverage a covergroup in a uvm_subscriber fed by the monitor's analysis port (Functional coverage) 10
